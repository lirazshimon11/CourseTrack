# מוסדות ולוחות אקדמיים — הפעלה ובדיקה

## עדכון: מסכים חדשים, הפצה אוטומטית וייבוא מערכת שעות

אם כבר הרצת את שתי המיגרציות הקודמות, הרץ **רק** את הקובץ החדש במלואו:
`supabase/migrations/202611060002_distribution_and_import.sql`.
לאחר הצלחה, דחוף את הקוד ל־GitHub והמתן לפריסת Vercel. אין צורך במפתחות או בשירות בתשלום נוסף.

- הגדרות → **ייבוא מערכת שעות מ־PDF** (זמין גם ממסך הקורסים). הקובץ מעובד מקומית בדפדפן, ללא שליחה לשרת או ל־AI. אפשר גם להדביק פלט מהסקריפט המקורי. מאשרים שנה, סמסטר, קורסים ופרופיל לפני שמירה.
- הגדרות → **המוסד והסמסטרים שלי**: בחירת מוסד מפיצה את הלוחות שלו לחשבון. עדכון של לוח שפורסם מתעדכן אוטומטית בעותקים המקושרים. תאריכים ששונו ידנית מסומנים בצהוב ונשמרים. אפשר לחזור לעדכוני מוסד באישור מפורש.
- הגדרות → **מרכז ניהול**: בחירת מוסד, סיכום הבדיקה האחרונה, הצעות לאישור; היסטוריה, הגדרות סנכרון ובדיקות מפתחות נפתחות לפי צורך. משתמש רגיל אינו מקבל גישה לכלי הניהול גם בכניסה ישירה לנתיב.
- עריכות מנהל ידניות וממצאי חילוץ עמומים דורשים אישור מנהל. לוח חדש תקין יכול להתפרסם אוטומטית כשהאפשרות פעילה. ההפצה למשתמשים אוטומטית לאחר הפרסום. שנה חדשה נוספת לרשימה; השנה הפעילה הקיימת אינה מוחלפת אוטומטית.
- כל ריצת Cron בודקת גם גישה ניהולית של השרת ושומרת סיכום ללא סודות ב־`calendar_health` (קריאה למנהלים בלבד). בדיקה ידנית מאמתת בנוסף את החשבון המחובר. בדיקה אוטומטית שלא הצליחה להתחבר למסד לא תוכל לשמור בו תוצאה חדשה — יש לבדוק גם לוגים ב־Vercel.
- ייבוא נשמר בטרנזקציה אחת. קורס שכבר יובא לא מוכפל או מוחלף. מרצה, חדר וקוד מפגש נשמרים ב־`slots_data`; קוד קורס, נ״ז ושעות נשמרים בעמודות ייעודיות. נוכחות והערות קיימות אינן משתנות.
- שינוי תאריכים אינו בונה מחדש מפגשים של קורסים קיימים. הנתונים החדשים משמשים ליצירת קורסים חדשים.

בדיקה ראשונה: בחר HIT בחשבון, פרסם לוח דרך מרכז הניהול, וודא שהשנה מופיעה בחשבון נוסף המשויך ל־HIT. שנה שם תאריך ידנית, פרסם עדכון מוסדי, וודא שההתאמה נשמרת. לאחר מכן ייבא קובץ/פלט, בדוק את התצוגה ושמור. ייבוא חוזר צריך לדווח על דילוג על קורסים קיימים.

לתצוגת UI מבודדת עם נתוני דוגמה (ללא חשבון אמיתי): `node scripts/preview-ui.mjs`, ואז `http://127.0.0.1:8082/settings`. שרת זה אינו חלק מהאפליקציה או מהפריסה. האתר האמיתי רץ באמצעות `npm run web`; ה־API מופעל ב־Vercel.


## 1. SQL

אם מיגרציית החשבונות הקודמת טרם הופעלה, מפעילים קודם את:
`supabase/migrations/202611050001_accounts.sql`.

לאחר מכן מעתיקים ל־Supabase SQL Editor את **כל** הקובץ:
`supabase/migrations/202611060001_institution_calendars.sql` ומריצים פעם אחת.

המיגרציה החדשה נבדקה במסד Postgres מקומי עם טבלאות הבסיס הצפויות. היא טרם הורצה בפרויקט האמיתי שלך. אם מתקבלת שגיאה, שולחים אותה לפני שממשיכים; הפעולות עטופות בטרנזקציה.

הטבלאות החדשות:

| טבלה | תפקיד |
| --- | --- |
| `institutions` | רשימת מוסדות. HIT נוצר במפורש כמכון טכנולוגי חולון. |
| `institution_calendars` | לוח משותף לכל מוסד ושנה; תאריכים, ימים ללא לימודים, מקור וגרסה. |
| `calendar_sources` | עמוד מקור קבוע למוסד, מצב סנכרון ומועד בדיקה. |
| `calendar_sync_runs` | תוצאות ריצה והצעות שממתינות לאישור מנהל. |
| `student_profiles` | מוסד נבחר, שנת לימודים פעילה ופרטי לימודים אישיים. |
| `app_admins` | הרשאות מנהל. לא ניתנות לעריכה דרך הדפדפן. |

טבלת `academic_years` הקיימת ממשיכה להחזיק את ההגדרות האישיות של כל משתמש, ונוספים לה קישור למוסד, קישור ללוח המקור, גרסת המקור וימים ללא לימודים. קורסים ושיעורים קיימים אינם משתנים. נתונים ישנים לא משויכים אוטומטית ל־HIT.

## 2. מינוי מנהל ראשון

נרשמים באתר, מאשרים את האימייל ומעתיקים את ה־UUID שלך מ־Authentication → Users. מחליפים את הטקסט הבא ב־UUID האמיתי ומריצים ב־SQL Editor:

```sql
insert into public.app_admins (user_id)
values ('YOUR_USER_UUID'::uuid)
on conflict do nothing;
```

לא משתמשים ב־user_metadata לקביעת הרשאות. כל חשבון שאינו בטבלה הוא משתמש רגיל. למנהל יש הרשאה לערוך מוסדות ולוחות משותפים, אבל אין גישה לפרטים האישיים של משתמשים אחרים דרך האתר.

## 3. בדיקת המסכים לפני חיבור הסנכרון

1. נכנסים לאתר → הגדרות → המוסד והסמסטרים שלי; כלי המנהל נמצאים במרכז ניהול נפרד.
2. בוחרים HIT ושומרים בפרופיל. אין מוסד שנבחר מראש למשתמש חדש.
3. כמנהל, יוצרים לוח ידני עם השנה הלועזית שבה מתחילה שנת הלימודים (תשפ״ז: 2026), תאריכים אמיתיים והערות. אין בקוד תאריכים מומצאים של HIT.
4. בוחרים "שימוש בלוח הזה בחשבון שלי". נוצר עותק אישי ונבחר כשנה הפעילה.
5. משנים תאריך בעותק האישי. הלוח המשותף והחשבון השני לא אמורים להשתנות.
6. מוסיפים מוסד נוסף כמנהל ולוח ידני עבורו. משתמש אחר בוחר אותו ורואה לוחות של המוסד שבחר בלבד.
7. נכנסים כמשתמש רגיל: כלי הניהול לא מוצגים, וכתיבה ישירה לטבלאות המשותפות חסומה ב־RLS.

בחירה בלוח אחר לא ממירה קורסים ישנים לשנה החדשה. אפשר לחזור לשנה הקודמת דרך "השנים שלי". שינוי בתאריכים או בחופשות חל על יצירת מפגשים חדשים בלבד; לא נמחקת נוכחות או הערה קיימת.

## 4. הגדרות Vercel חד־פעמיות

Project Settings → Environment Variables. מוסיפים לסביבת Production:

- `SUPABASE_URL` — כתובת הפרויקט הקיים.
- `SUPABASE_ANON_KEY` — המפתח הציבורי של אותו פרויקט.
- `SUPABASE_SERVICE_ROLE_KEY` — מפתח service_role של הפרויקט. נשאר בשרת בלבד, לעולם לא בקוד ה־frontend או במשתנה `EXPO_PUBLIC_*`.
- `CRON_SECRET` — מחרוזת אקראית ארוכה. ניתן ליצור מקומית: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. מזינים ישירות בהגדרות Vercel, אין צורך לשלוח אותה בצ׳אט.

משאירים את build command כ־`npm run build` ואת תיקיית הפלט כ־`dist`. משתמשים בגרסת Node התואמת ל־`pdfjs-dist` (Node 24 מתאים). פורשים מחדש אחרי הגדרת המשתנים.

ה־API נמצא ב־`/api/calendar-sync`. ה־rewrite של האתר החריג את `/api/` כדי לא להפנות בקשות שרת ל־index.html. משימת Vercel מוגדרת מדי יום ב־05:00 UTC. אין שירות תזמון חיצוני או API של AI. ההרצות צורכות מהמכסה הרגילה של Vercel.

Expo על localhost:8081 מציג את המסכים אבל **אינו מריץ את פונקציית השרת**. לבדיקת סנכרון משתמשים בפריסה ב־Vercel (או סביבת `vercel dev` מוגדרת). אפשר לבדוק את מקור HIT בקריאה בלבד בעזרת `npm run calendar:check` גם בלי מפתחות Supabase.

## 5. אימות הסנכרון הראשון

לפני בדיקת HIT אפשר ללחוץ על **בדיקת חיבור והרשאות עכשיו** באזור הניהול. הבדיקה מאמתת את החשבון והרשאת המנהל מול Supabase, בודקת שהמפתח הסודי מאפשר גישה לטבלת הרשאות שאינה נגישה למפתח ציבורי, בודקת את טבלאות הסנכרון ואת קיומו ואורכו של CRON_SECRET. היא לא פונה ל־HIT, לא משנה נתונים ולא חושפת מפתחות. אין צורך ב־SQL נוסף עבורה.

אישור של CRON_SECRET במסך הזה מעיד רק על הגדרת המשתנה. כדי לבדוק הפעלה באמצעות Vercel, מפעילים את המשימה דרך Cron Jobs בלוח הבקרה ובודקים את יומן הבקשות ואת יומן הסנכרון. כפתור הסנכרון באתר משתמש בהרשאת המנהל, ולא בסוד התזמון.

1. נכנסים כמנהל ובוחרים HIT → "בדיקת המקור עכשיו".
2. אם מופיעה תקלה, הלוחות הקיימים נשארים ללא שינוי. התוצאה מופיעה ביומן. בין ניסיונות ידניים יש להמתין עשר דקות.
3. כשהחילוץ מצליח, משווים את התאריכים ואת רשימת הימים ללא לימודים למקור ולוחצים "אישור ופרסום". אם החילוץ שגוי, דוחים ומתקנים את המתאם לפני הפעלת אוטומציה.
4. "פרסום אוטומטי של שנים חדשות" מאפשר גם אכלוס ראשון בלי משתמשים ובלי ריצה מאושרת קודמת. מיגרציית האכלוס מפעילה זאת ל־HIT.
5. שנה חדשה עם תאריכי סמסטר תקינים תפורסם אוטומטית. הערות על ימים חלקיים נשמרות לצד הלוח; מידע עמום ועריכות מנהל ידניות ממתינים לבדיקה. בחשבון המשתמש יש לבחור את הלוח החדש; שנים קודמות לא נדרסות.

החילוץ קורא HTML תחילה. אם אינו מצליח, הוא משתמש בקישור ההדפסה שהתגלה בעמוד. קישורים עמומים, סריקות ללא טקסט, תאריכים סותרים, הוראה במתכונת של יום אחר וחופשות חלקיות אינם מאושרים אוטומטית.

ב־6.11.2026 אומתה קריאה אמיתית של העמוד הרשמי וחולצו תאריכי תשפ״ז: סמסטר א׳ 18.10.2026–17.01.2027, סמסטר ב׳ 21.02.2027–04.06.2027 וקיץ 11.07.2027–17.09.2027. נבדק שהשנה הקודמת ברשימת הבחירה ותאריך פתיחת השנה הבאה אינם משנים את השנה המזוהה. ימים עם לימודים בזום, הפסקות חלקיות וימי השלמה מוצגים לבדיקה ואינם נמחקים כימי חופשה מלאים.

תוקנה שגיאת `UNABLE_TO_VERIFY_LEAF_SIGNATURE` על ידי השלמת שרשרת הביניים הרשמית של Let’s Encrypt בחיבור ל־HIT בלבד. התעודות מאומתות מול שורש מוכר של Node, ואימות שם המתחם והתוקף נשאר פעיל. התיקון כולל את קובץ התעודות הציבוריות בפריסת Vercel; אין צורך בשינוי משתני סביבה או SQL. הסבר ומקורות נמצאים ב־`server/certificates/README.md`.

לאחר פריסת התיקון לוחצים "בדיקת המקור עכשיו". אם מופיעה הודעת המתנה, ממתינים עד שעברו עשר דקות מהבדיקה הקודמת. צפויה תוצאה "ממתין לבדיקה" עם תאריכי השנה והחריגים. השינוי אומת מול HIT מהסביבה המקומית; יש להשלים בדיקה זו גם מהפריסה ב־Vercel.

האוטומציה כרגע נתמכת עבור HIT בלבד. מוסדות אחרים עובדים עם לוחות ידניים; תמיכה אוטומטית עבור מוסד נוסף דורשת מתאם למבנה האתר שלו והוספת מקור מאושר, ולא שינוי בהפרדת הנתונים.

## 6. בדיקות מקומיות שבקוד

```text
npm test
npm run check
npm run build
```

הבדיקות כוללות הרצה אמיתית של שלוש המיגרציות ב־Postgres מקומי (PGlite), RLS בין שני משתמשים, הגבלת מנהלים, הפרדה בין מוסדות, העתקה אישית ללא דריסת נתונים, מניעת ריצות חופפות, חילוץ שנה דינמית וגבולות תאריכים, ומניעת גישה לכתובות לא מורשות.

ייבוא ה־PDF מותאם כעת למבנה HIT על בסיס קוד החילוץ ופלט הדוגמה. הפלט נבדק כ־8 קורסים ו־14 מפגשים שבועיים. קובץ אישי אמיתי לא נמסר ולא נבדק במהלך הפיתוח; יש לבדוק את תצוגת הייבוא במכשיר שלך. קבצים סרוקים או מוגני סיסמה אינם נתמכים. מוסד אחר עשוי לדרוש התאמת החילוץ למבנה הקובץ שלו.


## זיהוי אוטומטי של סמסטר בייבוא

בחירת המוסד מספיקה. במסך הייבוא מוצעת שנת הלימודים והסמסטר לפי תאריכי הלוחות בחשבון, בשעון ישראל. במהלך סמסטר הוא נבחר; בתקופת מבחנים או חופשה נבחר הסמסטר הבא שפורסם. אין הנחה ששנת לימודים מתחלפת בינואר. אפשר לשנות לסמסטר אחר או לשנה אחרת מתוך אותו אזור, לפני שמירה. לאחר הייבוא השנה שנבחרה הופכת לשנה הפעילה להצגת הקורסים.

קובץ שמציין סמסטר אחר גורם להערה, ולא משנה את הבחירה בשקט. כשאין לוח נוכחי או עתידי שפורסם, האפליקציה מבקשת פרסום לוח ממנהל ואינה ממציאה תאריכים. שינוי UX זה אינו דורש SQL נוסף מעבר למיגרציות שכבר סופקו.


## שליפה אוטומטית ללא תאריכים ב־SQL

`supabase/migrations/202611070001_hit_calendar_bootstrap.sql` מכיל כעת רק הגדרת מוסד, כתובת מקור והפעלת האוטומציה. אין בו שנה, תאריכי סמסטר, חופשות או תוכן של לוח. אם הרצת את הגרסה הקודמת, אפשר להריץ את הקובץ המתוקן שוב; הוא אינו מוחק נתונים קיימים.

בסיום build של Vercel Production מופעל אותו handler שמשמש את משימת התזמון. הוא קורא את המקור העדכני, מחלץ את השנה והתאריכים, מאמת אותם ושומר ב־institution_calendars. ריצה נוספת מתוזמנת מדי יום ב־05:00 UTC. אין תלות בבחירת מוסד, כניסת משתמש או קיום משתמשים. preview/build מקומי לא משנה את Supabase.

לוח חסר מתווסף; לוח שיובא בעבר מתעדכן אם המקור השתנה; שנה חדשה נשמרת כלוח נוסף. שגיאה או חילוץ לא תקין משאירים את הלוח הקודם. לוח שהמנהל ערך ידנית מוגן מהחלפה אוטומטית. ימים חלקיים והשלמות נשמרים בהערות. השינויים מתפזרים באמצעות מנגנון ההפצה שכבר הותקן, בלי לדרוס התאמות משתמשים.

להפעלה: הרץ את SQL ההגדרות המתוקן, ואז דחוף ופרוס ב־Vercel עם משתני השרת שכבר הוגדרו. ה־build חייב לרוץ דרך `npm run build`, כדי ש־postbuild יופעל. בדוק ב־Build Logs את `Calendar initialization` ובמרכז הניהול את תוצאת הריצה. כשל שליפה אינו מכשיל את בניית האתר; הוא מופיע ביומן והריצה היומית מנסה שוב.

בחירת מוסד אצל משתמש נשמרת מיד, והסימון מופיע רק לאחר שמירה מוצלחת. האפשרות הראשונה היא ״לא נבחר מוסד אקדמי״. הבחירה מקשרת לנתונים המרכזיים, ואינה מפעילה שליפה מהמקור.


## ביטול שער האישור

מקור פעיל שולף, מאמת ושומר לוח אוטומטית. אין תלות בדגל הישן `auto_publish_new_years`, ואין דרישה לאישור מנהל לפרסום ראשוני או לעדכון לוח מיובא. רענון מקור מצליח סוגר הצעות ישנות של אותה שנה ככאלה שהוחלפו בשליפה חדשה. נתונים לא תקינים מדווחים ככשל והלוח הקודם נשמר. עריכה ידנית של מנהל נשמרת ללא החלפה ואינה מייצרת בקשת אישור. אין צורך ב־SQL נוסף לשינוי זה: לאחר פריסה אפשר ללחוץ ״בדיקת המקור עכשיו״, או להמתין לתזמון האוטומטי.


## צבעים אישיים לקורסים

יש להריץ את `supabase/migrations/202611070002_import_course_colors.sql` לפני פריסת בורר הצבעים. העדכון משנה רק את פונקציית הייבוא כדי לשמור את צבע הקורס שנבחר, במקום צבע קבוע. קורסים קיימים אינם נצבעים מחדש, וייבוא חוזר עדיין אינו דורס אותם. בתצוגה המקדימה כל קורס מקבל צבע שונה, והמשתמש יכול לשנותו לפני שמירה. ניתן לשנות צבע גם בעריכת קורס לאחר הייבוא.
